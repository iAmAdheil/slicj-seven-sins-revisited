### Slide 1: Seven Sins Revisited

**Adheil**, about 30 seconds

Good morning. I am Adheil, and this is Om. Our project starts from an ICSE 2019 paper called The Seven Sins, about security smells in infrastructure as code. We did three things. We rebuilt the paper's tool. We extended the tool to two more technologies. Then we reduced its false alarms with a decision model. I will cover the rebuild and the extension. Om will cover the false alarms.

### Slide 2: One insecure line reaches every server

**Adheil**, about 55 seconds

Site reliability teams configure whole fleets with scripts. This example comes from the paper, and it is a real open source Puppet script. The password is written directly in the script. Every server that runs this script gets that password. The paper calls this a security smell. A smell is not always a vulnerability, but it needs a review. The paper's linter, SLIC, reported 0.99 precision on its own test set. Later, an independent team tested it on a different test set. Its precision for hard-coded secrets was 0.10. So nine of ten secret findings were false alarms. That gap is the reason for this project.

### Slide 3: The paper: seven smells and one linter

**Adheil**, about 50 seconds

The authors studied 1,726 Puppet scripts by hand and derived seven smells. Each smell maps to a CWE weakness. They then built SLIC. SLIC has two parts. A parser turns a script into tokens with a name and a value. A rule engine matches string patterns on those tokens. For example, if a name contains 'password' and the value is a non-empty string, SLIC reports a hard-coded secret. The authors scanned 15,232 scripts and found 21,201 smells. When they asked developers, 64.4 percent of the 104 replies agreed with the finding. Developers who disagreed often gave context as the reason. Remember that point, because it comes back later.

### Slide 4: We asked four research questions

**Adheil**, about 40 seconds

We asked four questions. First, can SLIC be rebuilt from the paper? Second, does the approach port to Ansible and Chef, and can it find a new kind of smell? I will answer these two. Third, can a decision model remove false alarms, and what does that cost? Fourth, can an attacker fool that model with a comment in the script? Om will answer these two.

### Slide 5: We tested on labels that we did not write

**Adheil**, about 60 seconds

A claim needs a fair test, so we did not label the main test data ourselves. We used the three test sets that the GLITCH authors published at ASE 2022. They contain about 80 scripts per technology and 176 scored smells, with a line number for each smell. Before we trusted our scorer, we checked it. It reproduces all 77 published per-smell values for SLIC, SLAC and GLITCH. We also ran the authors' original SLIC on this machine. Its output matched the published output on all 120 findings. To limit overfitting, we refined rules only on a fixed 30 percent of the files. For the triage experiment we used 5-fold cross-validation, grouped by file, with 10 seeds.

### Slide 6: RQ1: the paper alone is not enough

**Adheil**, about 55 seconds

We built SLIC twice. The first version uses only the rules that the paper prints. It agrees with the original tool on 58 percent of findings, measured with Jaccard overlap. It shares 73 findings, misses 47, and adds 5. The second version copies the released Ruby code token by token. It shares all 120 findings and adds 1. That one extra comes from a .pp file that contains Haskell-style comments, not Puppet. So the tool is reproducible from the code, but not from the paper. One more result: on this independent test set, the original SLIC has micro precision 0.28, far from the 0.99 that the paper reports on its own test set.

### Slide 7: Six differences between paper and code

**Adheil**, about 60 seconds

We traced the gap to six differences. The printed admin rule requires 'admin' and 'user' in the name. The paper's own example has 'admin' in the value, so the printed rule misses it. The private-key pattern is not a valid regular expression as printed. The secret rule in the code is much wider than the table. The weak crypto rule flags any token, not only functions. The comment rule uses more keywords. The sixth difference is my favourite. One rule prints a tag that ends in three colons. The driver searches for a tag that ends in an underscore. The two strings never match, so this check never reaches the report. Enabling it would add 11 findings on this test set.

### Slide 8: RQ2: the port competes with a current tool

**Adheil**, about 55 seconds

SLIC-J is our port. For Ansible we walk the YAML and keep line numbers. For Chef we read the Ruby line by line. We compared F1 with the current GLITCH release, which we ran ourselves. On Puppet and Chef, SLIC-J is slightly ahead. On Ansible, GLITCH is ahead. The authors' original tools are lower on all three. I must add one caution. We refined our rules on 30 percent of these same test sets, and GLITCH was not tuned on them. So read this as competitive, not as better. Precision on hard-coded secrets stays low for every tool, between 0.19 and 0.44 for us. That is the problem Om will address.

### Slide 9: A new smell: TLS checks turned off

**Adheil**, about 50 seconds

We also added an eighth smell. Turning off TLS certificate checks makes HTTPS open to an active attacker, and the seven sins do not cover this. SLIC-J finds it in any module, not only in specific ones. In the corpus, it appears in 1.01 percent of Ansible scripts, with 2,048 occurrences. It is rare in Puppet and Chef. The test sets have no labels for this smell, so we checked a random sample of 60 findings. 59 were correct, with one rater. The one false alarm was a test that asserts verification stays on. That is the end of my part. Rules give high recall, but too many false alarms. Om will now show how we reduce them.

### Slide 10: Rules propose, a model decides

**Om**, about 70 seconds

Thanks, Adheil. We keep the rules, because they are cheap and deterministic, and they find most smells. We add a step behind them. First, code collects facts about each finding: is the value a literal or a variable, does it look like a placeholder, is it a known key format, where does the URL point. Second, code masks anything that could be a working secret. The model sees only the shape of the value. Third, a decision model answers one question: is this a genuine instance of this smell, by this definition? We use TypeSafe Jev. It does not write text. It returns a probability. Fourth, code makes the final decision with a threshold tuned on training folds. So the model is one replaceable part, and code stays in control.

### Slide 11: RQ3: precision up 0.22, recall down 0.05

**Om**, about 55 seconds

We tested 269 candidate findings: 151 true and 118 false. The rules alone have precision 0.56 and recall 0.86. With Jev and the full context, precision rises to 0.78 and recall falls to 0.81. F1 rises from 0.68 to 0.80. Recall counts all 176 labelled smells, so the rules' own misses count against us. The result is significant. In a paired test, the triage step corrected 80 decisions and broke 9. The McNemar p-value is about 2 times 10 to the minus 15. A file-level bootstrap gives an F1 gain of 0.125, with a 95 percent interval from 0.08 to 0.18. Context also helped: the full state beat the flagged line alone by 0.03 F1, and that interval excludes zero.

### Slide 12: Most of the gain comes from secrets

**Om**, about 50 seconds

This chart shows precision per smell. Almost all of the gain comes from hard-coded secrets. False alarms fall from 80 to 4, and precision rises from 0.25 to 0.83. The price is 7 of 27 true secrets. These are mostly plain service names like nginx and zabbix, and placeholder passwords like foo. The labels count these as smells, but a reviewer may call them harmless. HTTP does not change, because Jev keeps all those findings. Many HTTP 'false alarms' look real to us, for example http colon slash slash download dot sonatype dot com. So those may be missed labels in the test set. The values on this slide come from one cross-validation seed.

### Slide 13: A chat model is not significantly better

**Om**, about 55 seconds

We replaced Jev with other models. The API makes that a one-line change. Claude Haiku has the highest F1, 0.81, but the paired difference to Jev is not significant: p is 0.33, and the interval includes zero. Haiku costs about four times more and takes about three times longer per call. Jev costs 0.035 dollars per thousand findings. Most decision models land between 0.75 and 0.80. Two are no better than the rules alone. So we conclude: pin the model version, and test before you trust a model. Jev also beats a simple logistic regression in paired decisions, but its F1 interval includes zero. We do not claim that Jev is the best model. We claim that this design works, and the model can be replaced.

### Slide 14: A surprise: practitioner context hurt F1

**Om**, about 45 seconds

Here is a result we did not expect. The original paper quotes developers who reject findings because of context, for example 'it's using http on localhost, what's the risk?'. So we wrote a filter with those arguments. It drops placeholder passwords, loopback URLs and similar cases. It made F1 worse: 0.64 against 0.68 for rules alone. Recall fell from 0.86 to 0.74. The reason is the test set. Its raters label a password like 'vagrant' as a smell, because by definition it is one. A developer may still not fix it. So 'is it a smell?' and 'should we fix it?' are two different questions, and this test set answers only the first. A future study should label both.

### Slide 15: RQ4: one comment can fool the model

**Om**, about 70 seconds

Anyone who can open a pull request can add a comment. So we inserted one comment next to each true finding and measured how often the model changed its mind. We used three texts: a false claim that the value is a dummy, a false claim of security approval, and a direct instruction to answer false. On the decision model, the direct instruction above the line flips 97.5 percent of true findings. Claude Haiku ignores that instruction, but it believes the dummy-value claim: up to 20 percent flip. Then we tested a fix: remove all comments from the model's input. Flips fall to 1.6 percent or less, with no loss of accuracy. Our first fix missed one field, the flagged line, and 45 percent of inline attacks still worked. So a fix must cover every field. Two cautions. These rates are at each model's tuned threshold, and backup slide 18 shows a threshold of 0.5, where rates are higher. Also, the API credit ran out, so we did not run this on Jev itself.

### Slide 16: What our results do not show

**Om**, about 55 seconds

We want to be clear about the limits. The test sets are small, and rare smells have fewer than ten instances, so per-smell numbers for those are weak. The labels contain noise. We refined the rules on 30 percent of the same files, so the candidate generator is not fully independent of the test data. Jev itself was not attacked in RQ4. The attack rates depend on the threshold. And one rater checked the TLS sample. All the code and the numbers are public, so anyone can check or extend this work.

### Slide 17: Three takeaways

**Om**, about 40 seconds

Three takeaways. One: publish rules as tested code, because the paper alone did not reproduce the tool. Two: keep rules in front and put a decision model behind them. Precision rose from 0.56 to 0.78 for a few cents per thousand findings. Three: keep comments out of the model's input, because one comment can reverse its decision. The code, data links and paper are on GitHub. Thank you. We are happy to take your questions.

## Likely questions

**Q: Why did SLIC score 0.99 in the paper and much lower here?** (Adheil)

The test sets differ. The paper's raters labelled 140 scripts where most scripts had no smell. The GLITCH set was built to contain more smell candidates, and its raters use a wider admin definition. We cannot run SLIC on the paper's own set, because its figshare link now returns a 404.

**Q: Is your port really better than GLITCH?** (Adheil)

We do not claim that. It is ahead on Puppet and Chef and behind on Ansible. We refined our rules on 30 percent of these files, and GLITCH was not tuned on them. So 'competitive' is the correct word.

**Q: Why is the recall ceiling 0.858?** (Adheil)

The rules produce 151 of the 176 labelled smells. Triage can only drop candidates, so it cannot recover the other 25.

**Q: What is Jaccard and why use it?** (Adheil)

Shared findings divided by all findings of both tools. It measures whether two tools report the same things, not whether those things are correct.

**Q: Why is your any-smell rate lower than SLAC's?** (Adheil)

Our rules do not count variable references or lookups as hard-coded. The corpus also differs, so we cannot separate the two effects.

**Q: How do you stop overfitting?** (Om)

Thresholds and logistic weights are fit only on training folds, and folds are grouped by file. The remaining risk: rule refinement looked at 30 percent of the same files. We list that as a threat.

**Q: What is McNemar, and why a file-level bootstrap?** (Om)

McNemar compares two methods on the same items, using only the items where they disagree. We resample files because findings in one file are not independent.

**Q: Why Jev and not Haiku, which scored higher?** (Om)

The difference is not significant. Jev costs about a quarter as much and is about three times faster per call. The design does not depend on Jev. A team can use either model.

**Q: What is calibration, and is Jev calibrated?** (Om)

A calibrated 0.8 means about 80 percent of those cases are true. Jev is not well calibrated: ECE is 0.152. The hybrid is better at 0.073, so tune thresholds on your own sample.

**Q: Why are the RQ4 thresholds so low?** (Om)

F1 on this data rewards keeping almost everything, so the best threshold is near 0.05 to 0.12. That is why backup slide 18 also shows 0.5, where attack rates are higher.

**Q: Why was RQ4 not run on Jev?** (Om)

The OpenRouter free allowance ran out after RQ3. We used a free decision model and the Claude CLI. The script runs unchanged on Jev with credit. So we do not know Jev's own flip rate.

**Q: The Haiku arm ran through a CLI. Does that matter?** (Om)

The CLI loads a user-level instruction file, so the context is not empty. It is the same for clean and attacked inputs. On RQ3 the CLI arm scores F1 0.809 and the API arm 0.811, so the two paths agree closely.

**Q: Does masking fully protect secrets?** (Om)

No. It masks values that do not look like placeholders or plain identifiers, and lines with a sensitive name. A secret on a line with an unrelated name can reach the model. It reduces exposure. It does not remove it.

**Q: How does this differ from IntelliSA (MSR 2026)?** (Om)

IntelliSA also uses rules and then a neural filter, and it reports F1 83 percent on its own data. We add a verified reproduction of SLIC, a new smell, a comparison of decision models, calibration, secret masking and a prompt-injection test. The data sets differ, so the F1 values are not directly comparable.
